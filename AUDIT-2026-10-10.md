## 1. Bottom line

1. **The solver maths is sound.** Mass balance closes to 1e-13 on both days, CFL and numerics guards are tested, units and labels (`simulated` / `assumption` / `estimate`) are honest throughout. **[verified]**
2. **The 3 Oct output shown in the app is a boundary artefact, not a flood map.** The Urgell run is a 3.2 x 3.2 km box with **closed edges and zero boundary outflow**. 56% of all rain that day is still sitting in the box at midnight, peaking at **4.17 m on La Rambla**. That is a bathtub, not a street. **[verified]**
3. **Against the city's own flood atlas, the model currently performs at chance level.** Inside the box, top-10 hotspots hit 2 of 7 RESCCUE points within 300 m, versus 21-22% for random points. On 3 Oct the "high + severe" street layer covers so much of the box that 97% of random points are within 300 m of it, so it cannot discriminate anything. **[verified, n=7, so insufficient evidence to say better or worse than chance]**
4. **The 2 Oct output is physically plausible** (max 0.31 m, 2,002 of 2,224 segments dry) and is the safer day to demo. **[verified]**

For the hour left: do **not** retrain or rebuild. Fix the honesty of what is shown, add a visible validation panel, and do the 3D/glass UI on top. Details in section 5.

## 2. The critical finding: closed-box ponding

### Evidence **[verified]**

| | 2 Oct | 3 Oct |
|---|---|---|
| Rain into box | 113,000 m3 | 1,044,720 m3 |
| Drainage (assumed 20 mm/h) | 105,875 m3 | 444,692 m3 |
| Infiltration | 6,984 m3 | 10,516 m3 |
| **Boundary outflow** | **0** | **0** |
| **Storage at end of day** | 140 m3 | **589,652 m3 (56% of rain)** |
| Max depth | 0.31 m | **4.17 m** |
| Severe segments (>= 0.5 m) | 0 | **427 of 2,224** |

Top 3 hotspots on 3 Oct:

| Rank | Street | Peak | Minutes above 0.10 m | DEM pit depth | Distance to downhill (east) box edge |
|---|---|---|---|---|---|
| 1 | La Rambla | 4.17 m | 681 | **0 m** | **225 m** |
| 2 | Carrer de Sant Pau | 3.54 m | 673 | 0.60 m | **277 m** |
| 8 | Rambla del Raval | 1.61 m | ~670 | 0 m | **218 m** |

### Why it happens **[verified in code]**

- `solver/grid.py:221-236`: water may only leave at **sea cells (DEM <= 0 m)** or **river edge cells (DEM <= 10 m, Besos/Llobregat)**.
- The Urgell box (Eixample, Raval, Sant Antoni, Sants) has neither. So every edge is a wall.
- Barcelona drains NW to SE toward the sea. The east/south edges of the box are therefore the downhill side, and water piles up against them.
- La Rambla has **zero DEM depression** (`depression_depth = 0`, slope 2%). It is not a pit. It is where the wall is.
- `docs/audit/gates_report.md:380` says "Subdomain-cut edges carry critical-depth outflow". That is true for the **mitigation** subdomains, but **not** for this run (`boundary_outflow_volume = 0`). The gate passed on a different configuration than the one bundled into the app. **[verified]**

### Secondary contributors **[likely]**

- Uniform 20 mm/h drain sink: on 3 Oct, rain peaked well above that, so excess has nowhere to go except the walls.
- Building cells as +100 m walls channel flow into street canyons, amplifying the pile-up.
- 1 m DEM vertical rounding creates small flats (affects Sant Pau, depression 0.60 m).

### What does NOT look wrong **[verified]**

- Mass conservation, CFL, Green-Ampt parameters (Rawls 1983), Manning lookups, time-window handling (Madrid day, not UTC).
- Labelling discipline: every number carries `kind`, CONDITIONAL is shown, drainage is clearly an assumption.
- Mitigation deltas are internally consistent, but **saturated on 2 Oct**: +20 mm/h drainage removes 100% of flooded length. That makes the comparison uninformative (every lever "wins"). **[verified]**

## 4. Validation results (run today)

Script: in-domain version of the repo's own `scripts/reports-vs-model.mjs`. Reference points restricted to inside the model box, random baseline (3,000 points, seed 42) sampled **inside the box**, not across the whole city. The existing script samples across the reports' bounding box, which is ~5x bigger than the model area and flatters the model. **[verified]**

### RESCCUE hotspots inside the box (n = 7)

| | Within 150 m | Within 300 m |
|---|---|---|
| 3 Oct top-10 hotspots | 0/7 (random 6%) | 2/7 = 29% (random 22%) |
| 3 Oct high + severe streets | 4/7 (random **81%**) | 6/7 (random **97%**) |
| 2 Oct top-10 hotspots | 0/7 (random 7%) | 2/7 = 29% (random 21%) |
| 2 Oct moderate+ streets | 1/7 (random 8%) | 2/7 (random 20%) |

Read this as: **no evidence of skill yet, and no evidence of no skill.** n=7 is too small. What it does prove is that the 3 Oct severe layer is so widespread it carries no location information. **[verified]**

Positive note: Paral·lel / Ronda de Sant Pau (a known RESCCUE and T10 point) is 200 m from a top hotspot and 64-82 m from a flooded street on both days. **[verified]**

## 5. What to do with 1 hour (ranked)

### Must do (credibility, ~20 min)

1. **Default the app to 2 Oct**, not 3 Oct. Real, plausible, defensible.
2. **Flag edge-ponding on 3 Oct in the UI.** Any hotspot within 400 m of the closed box edge with depth > 1 m gets a badge: "Edge ponding: the simulated box has no outflow here, depth is an upper bound." Cap the displayed depth as "> 1 m". No backend change needed; uses data already in the JSON.
3. **Add a "How well does it match?" panel** showing the table in section 4, generated by a script, with the honest sentence "7 reference points, too few to claim skill."

### Should do (fixes the science, only if a rerun fits the time)

4. **Rerun the Urgell box with critical-depth outflow on all four edges** via the existing `edge_outflow_mask` input in `GridInputs` (`grid.py:76`). No solver code change. Runtime **[unknown]**; check `progress.log` from the last run before starting. If it takes more than 20 minutes, skip it and keep step 2.

### Do not do in this hour

- **Train an ML model.** With 7 positive points in the domain there is nothing to train on. Any accuracy figure would be noise dressed up. The repo's own `extra_ideas.md` also deprioritises "black-box predict-next-flood-cell". The ML proposal file you mentioned never reached me; if it contains a specific model I will assess it against this constraint.
- Re-tune drainage capacity to "match" RESCCUE. That is fitting to 7 points.

### After the hackathon: the model to iterate with

A **terrain null model** to beat, then the physics on top:
- Height Above Nearest Drainage (HAND) + topographic wetness index from the same DEM. Zero training, takes minutes, is the standard baseline in urban flood screening.
- Score both the solver and the null model with the same in-domain hit-rate + random baseline, on the **full city grid** (all 14 RESCCUE + 5 T10 + proof points, n ~ 25).
- Only if the solver beats the terrain baseline does the physics earn its complexity. If you later want ML, use a logistic regression on (slope, D8 area, depression depth, HAND, sealed fraction, distance to buried stream), with spatial block cross-validation, labelled "susceptibility, not probability".

## 6. Frontend notes for the UI work

- Map: MapLibre 5, `dragRotate: false`, no pitch, relief is a static PNG overlay. 3D terrain is possible with a `raster-dem` source (AWS Terrarium tiles, public, no key) plus `map.setTerrain()`.
- The street layer is drawn flat with `line` layers; with terrain enabled MapLibre drapes them automatically.
- Layout is phone-first with `pad()` in `MapCanvas.tsx` mirroring CSS rail widths. Any rail size change must update both.
- Existing tests: `npm run qa` (data contract + forbidden phrases), `signals:check`, `test:city-actions`, `reports-vs-model.test.mjs`, `build` = `tsc --noEmit && vite build`.
